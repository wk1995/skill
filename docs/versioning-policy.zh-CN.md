# 版本升级约束

语言：[English](versioning-policy.md) | 简体中文

本文先说明适用于不同版本格式的升级原则，再记录本仓库当前执行的具体规则。
通用版本不限定为三个数字；组件数量、字符类型及每部分含义由项目约定。
本仓库的发布规则适用于今后的发布，不重新编号历史版本；CI 校验格式、递增和声明，
评审判断兼容性依据是否真实反映实现。

## 通用版本格式

版本由项目定义的若干部分组成，可以是两段、三段、四段或其他数量；
每段可以是数字、字母、枚举标签或混合内容，分隔符也由项目定义。
例如 `1.2`、`1.2.3.4`、`A.B`、`1-rc-7` 都可以成为项目版本格式，
但不能仅凭字符串外观推断各段含义或升级方式。

项目应先明确每段的含义、允许值、先后顺序、后继规则、重置值，以及是否允许改变段数。
数字计数段的一步通常是加一；字母或枚举段必须使用明确约定的后继表，
不能自行假设 `Z` 之后是什么，也不能按字典序代替项目规定的版本顺序。
没有单独“功能段”的两段版本，可以明确约定兼容功能与修复共用一段；
四段版本的额外部分也必须有定义，不能自动把第四段当作无关后缀。

新项目未指定初始版本、且项目规则也未规定时，默认数字 `0.0.1`。
若明确指定的两段、四段或字母格式无法表示该值，先确定符合格式的初始值，
不能为套用默认值改写格式；已有发布不重置。可复用操作见
[version-upgrade-policy Skill](../skills/version-upgrade-policy/README.zh-CN.md)。

## 本仓库当前格式与归属

下面是本仓库 CI 当前实现的具体格式，不是对其他项目版本形式的通用限制。
本仓库保存的 Skill、适配器和产物版本采用 `MAJOR.MINOR.PATCH`（`x.x.x`），匹配
`^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`。
每一部分都是非负十进制整数，并非只能有一位，`1.2.10` 是合法版本。
保存的发布版本不允许前导零、`v` 前缀、预发布后缀或构建元数据。
`skill/example/v1.2.3` 中的 `v` 属于标签命名，不属于版本值。

分别评估以下版本，不联动抬升：

| 版本归属 | 兼容性边界 | 发布记录 |
| --- | --- | --- |
| Skill `SKILL.md` → `metadata.version` | 通用工作流、触发规则、输入、输出、安全行为及支持的前置条件 | `skills/<skill>/CHANGELOG.md` |
| 适配器 `adapter.json` → `version` | Agent 适配、发现和构建配置契约 | `platforms/<agent>/CHANGELOG.md`，注明适配器版本 |
| 适配器 `adapter.json` → `artifact_version` | 可安装包内容及其使用方契约 | `platforms/<agent>/CHANGELOG.md`，单独注明产物版本 |

不能把一个组件的升级级别直接复制给另一个组件。仅打包变化不提升通用 Skill 版本。
发布包应与自身的上一个版本比较，包括包内 Skill 的变化。
归属细节见 [Agent Build 架构](agent-build-architecture.md)。
整数型 `schema_version` 和用户外部项目的版本不受上述仓库具体格式约束。
读取历史或外部版本字符串不等于发布仓库版本，因此本文不收紧同步解析器的兼容范围。

## 版本各部分如何选择

与同一组件的上一次发布比较，先判断兼容性影响，再选择项目赋予相应含义的部分。
选择足以表达全部变更的最低级别，不依据总共有几段或每段是不是数字来决定。

| 变更影响 | 通用升级规则 |
| --- | --- |
| 兼容修复、等价优化 | 推进项目约定的维护部分 |
| 兼容的新能力 | 推进项目约定的功能部分；若与维护共用一段，遵循共同规则 |
| 破坏已有契约 | 推进项目约定的兼容性部分，并给出迁移依据 |
| 没有需要发布的行为或契约变化 | 保持版本不变 |

一次发布只推进最高必要级别一次。更高优先级部分保持不变，更低优先级部分按
项目约定重置或保留；重置值不一定是 `0`。顺序也不能仅凭左右位置推断。

以下例子各自使用明确的项目约定，不是所有同形版本都适用的规则：

| 格式与约定 | 一次升级示例 |
| --- | --- |
| 两段数字：第一段兼容性，第二段兼容更新；第二段初始值为 `0` | 修复 `1.2 → 1.3`；不兼容改动 `1.2 → 2.0` |
| 四段数字：依次为兼容性、功能、维护、构建；低位重置为 `0` | 修复 `1.2.3.4 → 1.2.4.0`；仅构建修订 `1.2.3.4 → 1.2.3.5` |
| 两段字母：第一段兼容性，第二段维护；后继表 `A → B → C`，维护初始值为 `A` | 修复 `A.B → A.C`；不兼容改动 `A.B → B.A` |

### 本仓库的三段数字映射

本仓库当前将通用影响级别映射到 `MAJOR.MINOR.PATCH`；下表只描述这一具体约定。

| 级别 | 必须满足的条件 | 示例 | 从 `1.2.3` 升级 |
| --- | --- | --- | --- |
| PATCH：第三位，修订号 | 保持已约定的行为，修复错误或改进实现 | 小 bug 修复、结果等价的性能优化、内部重构、恢复已承诺的安全检查 | `1.2.4` |
| MINOR：第二位，次版本号 | 增加能力，原有受支持用法仍然有效 | 可选命令或参数、额外支持的工作流、兼容的输出扩展 | `1.3.0` |
| MAJOR：第一位，主版本号 | 破坏原有契约，已有合法用法或使用方必须调整 | 删除命令、可选输入变必填、缺少兼容处理的输出或存储格式变化、取消已支持环境 | `2.0.0` |
| 不升级 | 被版本管理的组件行为及契约未变 | README 错字修正、澄清已有说明、补测试、维护仓库贡献规则 | 保持 `1.2.3` |

Skill 的公开契约包括已约定的触发与不触发场景、操作流程、输出和安全保证。
收窄已支持的触发范围或不兼容地改变工作流，即使只改 Markdown，也可能需要 MAJOR。
新增触发场景只有在保留原有路由和排除规则时才属于 MINOR。
恢复已承诺行为属于 PATCH；新增不兼容的安全要求，即使由 bug 引发，也要按契约变化评估。
新增输出字段只有在受支持的使用方能够接受扩展时才属于 MINOR。

文件数、代码行数、提交次数、工作量和修复数量都不决定升级级别。
严重 bug 的兼容修复仍可属于 PATCH，一行不兼容改动也可能属于 MAJOR。
兼容性不明确时，先检查受影响的调用方并记录结论，不能为了“保险”直接提升第一位。

## 本仓库的递增方法与早期版本

- 选中的数字只加一，其右侧全部归零：PATCH `1.2.3 -> 1.2.4`，
  MINOR `1.2.3 -> 1.3.0`，MAJOR `1.2.3 -> 2.0.0`。
- 不按十进制个位进位：修复可以是 `1.2.9 -> 1.2.10`，
  兼容功能可以是 `1.9.7 -> 1.10.0`。
- 一次发布汇总全部待发布变更，只按最高必要级别升级一次。
  三个修复加一个兼容功能是 `1.2.3 -> 1.3.0`，不能每个提交都升一次，也不能无发布依据跳号。
- 新建实验性组件从 `0.1.0` 开始；明确建立稳定契约的组件可以从 `1.0.0` 开始。
- 本仓库在 `0.x.x` 阶段也保护已约定的兼容性：修复是 `0.2.3 -> 0.2.4`，
  兼容功能是 `0.2.3 -> 0.3.0`，不兼容改动提升主版本到 `1.0.0`。
  这是比“所有 `0.x` 契约都不稳定”更严格的仓库规则。
- 唯一不要求破坏兼容性的 MAJOR 例外是明确发布首个稳定版（`0.x.x -> 1.0.0`）。
  必须记录支持的契约和就绪依据，不能仅凭一个小修复或小优化宣称已具备稳定发布条件。

## 本仓库升级前必须记录的依据

修改版本前，在 PR 或变更说明中记录：

1. 组件及版本字段、上一次发布版本、计划版本。
2. 升级级别（或不升级）、用户可感知的变化及兼容性判断。
3. MAJOR 必须给出原有受支持用法、新行为、受影响使用方和迁移步骤。
   首个稳定版则提供稳定契约和就绪依据，并说明是否需要迁移。
4. 支持结论的测试或一致性检查，以及已知限制。

尚未发布的改动写入所属 changelog 的 `[Unreleased]`。
确定发布版本时，在同一次变更中添加版本标题、UTC 日期以及触发、安全和兼容性影响摘要。
多个待发布提交合并为一个发布条目。不得修改已发布条目以同一版本分发不同内容，
也不得通过降低发布版本撤销变更；应发布新的纠正版本。

仅修改仓库文档不需要发布 Skill。如果主动把更新的文档分发为新产物，
则评估产物的 PATCH 发布，保持行为未变的 Skill 和适配器版本。
根 README 中规划的 `.changes/` 流程不是前置要求，目前由变更说明和所属 changelog 承载依据。

## 本仓库 CI 校验

当前 `scripts/version_guard.py` 只执行下述三段数字规则，不解析上面的自定义两段、
四段或字母格式。其他项目采用通用规则时，需要按其格式实现并共享相应的解析与校验。

提交改动后运行 `python3 scripts/version_guard.py --base origin/main`。
必需的 `skill-catalog` 检查会在生成或提交目录前执行版本校验，
`tests/pr-review-gate.sh <base>` 也会执行它。CI 使用精确的 PR base SHA。
可选参数 `--head <commit>` 默认为 `HEAD`；未提交的工作区修改不参与校验。

合并或推送到仓库默认分支后，独立的 `default-branch-version` workflow job
使用该次 push 事件精确的 `before` 和 `after` 提交执行
`--mode push --base <before> --head <after>`。默认分支名称来自事件，不写死分支名。
其他分支以及分支创建/删除事件会跳过，因为它们不属于已有默认分支的前后版本比较。
该 workflow 仅有读取权限，不生成目录、不修改版本，也不撤销检查失败的合并。

push 模式要求历史向前推进，并比较实际结果树；回退、分叉历史或引用不可获取时检查失败。
比较范围是整次 push，而非 `HEAD^`：同一次 push 中连续执行
`1.2.3 -> 1.2.4 -> 1.2.5` 会失败，分成两次 push 则可以每次各加一。
已有版本为 `1.2.3` 时，升级后的值只能是 `1.2.4`、`1.3.0` 或 `2.0.0`，
并附带对应声明和依据；版本不变仍然允许。
PR 检查继续在合并前拦截这些错误，push 检查负责检测默认分支更新后的违规情况。

校验器读取 Git 提交中的文件，将 base 记录的版本与模拟合并结果比较。
默认分支的无关更新不会被误判为 PR 降级；有合并冲突时必须先解决。
它可能创建临时 Git 合并对象，但不修改工作区、暂存区、引用或版本文件。
缺少 Git、引用不存在、元数据格式错误、身份重复或发布记录不可读时都会失败。
组件目录及元数据不能是符号链接或子模块。Skill 元数据使用块状 YAML `metadata`
映射，`sync_id` 和 `version` 是其直接标量字段；适配器清单使用 JSON。
这两个 YAML 字段在 frontmatter 中各只能出现一次，且不能带行尾注释。
嵌套或其他位置的重复字段即使值相同也会被拒绝，确保 CI、目录生成器、构建器和同步工具
读取相同的身份与版本。上游版本请使用 `upstream_version` 等不同字段名。
此限制针对仓库输入，不改变外部同步的兼容范围。

CI 检查全部当前 Skill、适配器和产物的版本格式。新增组件或修改版本时，
必须在所属 changelog 中新增唯一标题的条目，使用合法且不晚于当前 UTC 日期的日期，
并填写以下非空字段：

```markdown
## [1.2.4] - 2026-09-10

- Change-Type: fix
- Summary: Correct handling of an already supported input.
- Compatibility: Existing inputs and outputs remain supported.
```

Skill 和适配器使用 `## [<version>] - YYYY-MM-DD`；
产物使用 `## [artifact <version>] - YYYY-MM-DD`，避免适配器与产物版本相同时误用同一份依据。
字段必须是对应发布章节内的单行 Markdown 列表项；字段名和枚举值始终使用英文。
反引号或波浪号围栏代码块、HTML 注释中的标题和字段不属于发布依据，
也不计作重复条目或已发布的历史版本。

| `Change-Type` | 允许的版本变化 | 额外必填字段 |
| --- | --- | --- |
| `fix` | PATCH + 1；包括兼容优化、重构或产物文档维护 | 无 |
| `feature` | MINOR + 1，PATCH = 0 | 无 |
| `breaking` | MAJOR + 1，MINOR = PATCH = 0，包括 `0.x.x -> 1.0.0` | `Breaking-Change`（旧/新行为及受影响使用方）、`Migration`（迁移步骤） |
| `stable` | 仅限 `0.x.x -> 1.0.0` | `Stable-Contract`、`Readiness` |
| `initial` | 新组件使用 `0.1.0` 或 `1.0.0` | 使用 `1.0.0` 时填写 `Stable-Contract`、`Readiness` |

声明为 `fix` 的发布不能把 `1.2.3` 改成 `2.0.0`。
降级、跳号、低位未归零、重复或复用发布标题、缺少声明都会失败。
Skill 通过不可变的 `metadata.sync_id` 匹配，目录改名不会重置版本历史。
原身份在其他路径延续时，新 Skill 可以使用释放的旧目录；新身份仍须满足首次发布规则。
适配器和产物分别按适配器 ID 检查各自的历史。

版本未变化时，以及已有的历史条目，不要求补填这些新字段；待发布变更仍可写入 `[Unreleased]`。
比较基线是 PR base 中记录的版本，而非远端发布标签。
CI 不推断实现变化是否必须发版、不判断破坏兼容性的声明是否属实，也不强制检查全部历史内容不可变，
这些仍由评审负责。历史或外部版本的同步解析、独立构建的解析继续保留兼容性；
本次严格发布格式的自动检查入口是仓库 CI 校验器。
