## 2. 背景与问题

用户希望在 Codex 使用过程中，通过 Skill 根据任务选择合适的模型，并通过记录实际效果不断改进选择策略。目前主要存在以下问题：

- 每次手动判断模型与推理强度，增加操作负担。
- 始终使用高能力模型可能增加耗时与用量；始终使用轻量模型可能增加返工。
- 任务复杂度会变化，例如从信息查找进入跨模块设计，最初选择不一定适合后续阶段。
- 使用日志能够提供耗时、用量和失败信号，但缺少“为什么选这个模型、最终是否有效”的对应记录。
- 模型推荐、请求执行和实际生效容易混淆，用户需要知道自己看到的是建议还是已经执行的选择。

现有 `codex-usage-improvement` 提供会话元数据汇总和经验记录，入口为 `review`、`record`、`list`。当前会话汇总只保留最后观察到的模型，尚未建立每轮模型、选型决策与交付结果的完整关联。自动路由需要在此基础上补充能力。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 让用户用自然语言获得模型与推理强度建议，并理解主要原因。
2. 在支持的执行入口中，按用户已启用的策略自动选择模型，减少重复操作。
3. 每次选择均可追踪到任务、策略版本、实际执行模型与可观察结果。
4. 在交付质量可接受的前提下，改善任务完成时间或用量；允许用户选择偏重质量、速度或节省用量。
5. 通过可比较任务的历史反馈提出策略调整，并支持恢复此前策略。

### 3.2 非目标

- 不训练或微调模型，不把经验积累描述为模型自身权重发生变化。
- 不承诺仅安装 Skill 就能拦截桌面端所有输入、覆盖所有会话。
- 不承诺正在生成的一轮能够无缝切换模型。
- 不以修改全局默认配置冒充当前任务模型切换。
- 不把限额恢复、购买额度、跨账号执行或外部 API 付费调用纳入自动回退。
- 不在首期提供多 Agent 调度、团队共享、云端日志中心或自动编辑其他 Skill。
- 不将 token 数直接换算成订阅扣费或账单金额。

## 4. 可行性与入口边界

下表中的官方能力依据来自 2026-09-08 已读取的文档。运行时支持仍需按实际安装版本与账号验证。

| 场景 | 当前依据 | 产品承诺 |
| --- | --- | --- |
| Skill 判断任务并推荐模型 | Skills 可以提供指令、资源和脚本；未见自动切换模型的专用 Skill 元数据契约 | 首期支持推荐；不能只写配置字段就声称已切换 |
| CLI 指定模型启动执行 | 官方说明支持 `--model`，也适用于非交互执行 | 后续支持受控 CLI 入口；与桌面当前会话区分展示 |
| App Server 查询可用模型 | `model/list` 返回模型和支持的推理强度等信息 | 自动执行前通过适配器获取并校验可用候选 |
| App Server 同一任务下一轮指定模型 | `turn/start` 接受 `model`、`effort`；指定设置会成为后续轮次默认值 | 后续可验证轮次边界切换；不能假设参数只影响一轮 |
| 当前轮追加输入并切换模型 | `turn/steer` 明确不接受模型等轮次覆盖参数 | 当前轮只产生下轮建议，不声称已经切换 |
| 桌面端当前任务自动路由 | 当前环境任务工具包含部分模型覆盖能力，但覆盖全部输入、连接当前任务和 UI 同步尚未实测 | 单列兼容性验证；未通过时仅推荐，不显示自动执行已开启 |

Skill 被选中和读取时，当前模型已经在执行。要在用户请求的第一轮生成前完成选型，需要拥有请求发送入口的路由组件。若在当前对话中调用 Skill，再启动另一次模型执行，两次调用产生的耗时和用量均需计入，不能称为零开销切换。

## 5. 用户场景与交互

### 5.1 获取一次推荐

用户：“这次只改一段 README，帮我选合适的模型，优先快一点。”

系统识别任务范围、偏好和候选能力，返回模型、推理强度与简短理由。若只有推荐能力，展示“建议使用……；本轮模型未改变”。推荐示例中的模型必须来自当前可用列表；无法查询时说明可用性未验证。

### 5.2 为项目启用自动选择

用户：“这个项目后续任务按均衡策略自动选模型，只在我允许的模型里选择。”

系统保存项目策略和授权范围。后续经过受支持路由入口的请求自动执行，不对范围内的每次选择重复询问。页面或回复明确展示该策略覆盖的入口，例如“仅通过路由 CLI 启动的任务”；入口不可用时不能报告启用成功。

### 5.3 尊重手动指定

用户：“这次就用我指定的模型，推理强度用 high。”

该次明确选择优先于自动策略。若指定组合不可用，返回原因与可选方案，不悄悄换成另一个型号。单次指定默认只覆盖该次逻辑执行；若接口会持久化默认设置，适配器需要恢复此前值，或明确告知无法做到单次覆盖。

### 5.4 复杂任务升级

一个原先范围较小的修复发展为跨模块排查，现有能力未达到验收标准。系统在当前轮结束后提出升级；自动模式下仅在既定预算和升级范围内执行。授权失败、网络异常和依赖缺失应先被识别为环境问题，不直接归因于模型能力。

### 5.5 复盘选型效果

用户：“看看最近一周的模型选择，哪些任务可以更省，哪些需要更强？”

系统按项目、任务类型和策略版本展示样本数、成功情况、返工、耗时及用量。对于样本不足或缺少结果的数据，保留“未验证”，给出可测试的调整建议。

### 5.6 暂停与恢复

用户可以停止自动路由、恢复某个策略版本，或只保留推荐能力。停止后不再发起新的自动执行；正在运行的任务不被隐式取消，继续按原任务生命周期完成或由用户明确中止。

## 6. 分阶段范围

| 阶段 | 必须交付 | 不纳入该阶段 | 完成条件 |
| --- | --- | --- | --- |
| P0：推荐与记录 | 任务画像、模型能力校验、模型/推理强度建议、决策记录、结果反馈、复盘 | 自动启动任务、自动改变当前模型、自动调整策略 | 能完整展示“推荐—实际执行—结果”，缺失信息明确标注 |
| P1：受控自动执行 | 一种经验证的执行入口、启停设置、项目策略、范围内自动选择、有限回退、执行结果核对 | 桌面所有输入全覆盖、生成中途热切换 | 选型与实际模型一致；无重复执行；回退和停用行为可验证 |
| P2：历史优化 | 同类任务对比、策略变更建议、策略版本与回滚、小范围实验 | 无证据自动推广全局策略 | 可说明调整依据，并比较调整前后的质量、时间和用量 |

P1 建议优先验证 CLI 路由，或由本产品拥有生命周期的 App Server 客户端。桌面当前任务接入作为独立验证项，通过后才加入支持列表。P0 是明确可交付的首期范围；P1 才完成“自动选择并执行”的目标。

## 7. 功能需求

### F01 任务画像与偏好（P0）

- 输入包括任务目标、范围、任务类型、输入模态、已知验收条件和用户偏好。
- 首批任务类型为资料查找、文档修改、局部代码修改、跨模块实现、代码审查、复杂诊断；无法判断时使用 `unknown`。
- 偏好为质量优先、均衡、速度优先、节省用量；默认建议采用均衡，支持项目覆盖。
- 不强制用户填写完整表单。缺少的信息标记为未知；只有直接影响可执行性的关键缺项才阻止执行。
- 任务复杂度不能只按提示词长度或文件数量判定。

### F02 模型与能力发现（P0）

- 候选集合取账号/运行时可用模型、用户允许模型与任务能力要求的交集。
- 校验模型支持的输入类型和推理强度；记录发现时间、来源与运行时版本。
- 目录不可用时，P0 可以使用明确标注过期或待验证的候选生成建议；P1 必须能确认所选组合可执行，否则降为推荐。
- 不把推荐名单当作账号访问权限证明，不凭型号字符串推断能力。

### F03 选择模型和推理强度（P0）

- 先验证明确指定是否可执行，再应用任务级选择、项目策略和用户默认策略；历史建议只有成为有效策略版本后才参与选择。
- 在有效候选中结合复杂度和偏好选择模型与推理强度。推理强度与模型分别决策，不把最高强度当作默认最优。
- 冷启动以可解释规则为主；有足够可比较证据后再调整规则。首期不为分类另加一次付费模型调用。
- 输出包含选择结果、主要理由、假设、替代方案、策略版本与预期生效范围。
- 无合格候选时说明缺失能力，不强行选择不匹配型号。

### F04 显式模式与授权范围（P0 记录，P1 执行）

- 默认 `recommend`；用户启用后才进入 `auto`，停用后回到推荐或关闭状态。
- 自动范围至少包含项目/任务入口、允许模型、偏好、允许的升级规则和预算边界。
- 一次启用在约定范围内持续生效；更改允许模型、扩大项目范围或增加额外付费入口不视为原授权的一部分。
- 不以 Skill 隐式触发等同用户启用了自动路由，也不要求普通推荐获得额外授权。
- 提供单次覆盖、查看当前策略、暂停和恢复策略的自然语言入口。

### F05 执行与生效验证（P1）

- 创建决策后提交一次执行，记录返回的执行标识，核对实际模型与推理强度。
- 区分 `recommended`、`submitted`、`running`、`completed`、`failed`、`cancelled` 和 `unknown`；“请求已接受”不等于“已完成”。
- 查询不到实际模型时记录未知，不用请求参数回填为观测值。
- 传递任务所需上下文和工作目录；新执行不能假设自动继承当前桌面对话的全部上下文。
- 同一执行失败或超时后，先核对是否已被接受；状态不明时不自动重复提交可能写入数据的任务。
- 模型选择不改变任务原有的文件、工具、网络和外部操作权限。

### F06 回退与升级（P1）

- 每个逻辑执行默认最多一次自动模型回退或升级，且仍受用户允许集合与预算约束。传输重试不算模型升级，但必须避免重复执行。
- 模型不可用：可在已启用的备选集合中选择匹配项，并记录原因。
- 限额耗尽：不能假设换模型可以绕过共享限额；只有确认备选可用且策略允许时才继续。
- 质量未达标：需要可观察证据，例如验收失败且已排除明显环境原因；不得因一次命令非零退出就升级。
- 已发生代码修改或其他副作用的任务，升级前必须核对当前状态并生成接续信息，不从头盲目重跑。
- 执行状态不明、无有效备选或预算无法满足时，保留已完成工作并报告待处理状态。

### F07 决策和结果记录（P0）

- 以逻辑任务、轮次和执行尝试关联数据；同一轮的重复事件不重复累计。
- 推荐模型、请求模型与实际模型分开保存；一项未知不影响其他已知事实。
- 结果来源区分用户确认、可验证检查和模型自评；无反馈不能视作成功。
- 环境失败、模型不可用、质量未达标和用户取消分别计数。
- 保留推理强度、耗时、token 类型及来源；成本无可靠计价依据时留空。
- 活跃会话跨越统计窗口、累计 token、分叉或恢复带来的共享历史不得被重复计入；无法确定归属的数据标为不可比较。

### F08 持续改进（P2）

- 按项目、任务类型、复杂度、输入能力需求和验收方式分组比较。
- 样本数、缺失率和结果来源必须随建议展示。初始建议每组至少 10 个可比较且结果已知的任务才做量化趋势判断；这是产品试运行阈值，不代表统计显著性。
- 将证据转化为带适用范围的策略候选，例如“此项目的纯文档修改可尝试更快型号”。
- 新策略经用户接受或符合事先启用的明确策略更新规则后生效；首期 P2 默认人工接受。
- 自动选择使用已有策略，与自动修改策略是两个独立开关。
- 版本化策略，保留修改原因、证据和恢复入口；恢复影响后续执行，不抹除历史结果。

## 8. 数据要求

以下是产品字段要求，具体格式和迁移方式由技术设计确定。

| 数据对象 | 最小信息 |
| --- | --- |
| 任务画像 | 逻辑任务 ID、稳定项目 ID、任务类型、复杂度、模态、验收方式、偏好；未知项可空 |
| 路由决策 | 决策 ID、时间、策略版本、候选来源及有效期、推荐模型/强度、理由、模式、覆盖范围 |
| 执行尝试 | 决策 ID、尝试 ID、线程/轮次标识、入口、运行时版本、请求和实际模型/强度、状态及错误分类 |
| 使用结果 | 时间、各类 token、统计口径、验收结果、返工、用户反馈、证据来源、可比较性 |
| 策略版本 | 项目范围、偏好、允许模型、升级规则、预算、版本、有效状态及前一版本 |

数据默认在本机仓库外存储，复用现有 Skill 的外部状态定位约定。实际目录、锁、原子写入和保留期限在技术设计中定义。

- 只读推荐不创建持久记录；首次请求启用记录后，在既定项目和字段范围内自动追加，无需逐条确认。
- 决策指标记录与“确认一条永久经验”是不同操作，不把指标事件自动提升为经验规则。
- 默认不持久化完整提示词、源码、工具输出或认证信息；需要人工核验时采用最小必要引用。
- 项目使用稳定标识，不仅使用目录末级名称；跨项目汇总仍保留来源范围。
- 支持查看、按范围导出及清除记录；导出默认脱敏，清除范围需具体可见。
- 旧版经验日志继续可读，新增路由记录不能隐式覆写旧数据。
- 日志缺失、格式损坏或字段不支持时说明缺口；不得用零值伪装未知。

## 9. 效果衡量

### 9.1 可靠性指标

- **生效一致率**：实际模型与预期模型一致的执行数 / 实际模型可确认的执行数；同时展示实际模型未知比例。
- **记录完整率**：必需字段已知的执行数 / 已提交执行数；缺失项按类型统计。
- **选型负担**：用户为选择模型进行的手动操作次数 / 可比较任务数。
- **重复执行与越界选择**：验收场景中均要求为零。

### 9.2 使用收益指标

- **首次验收通过率**：首次尝试通过约定验收的任务数 / 有可判定首次验收结果的任务数。
- **返工率**：验收前需要纠正或再次实现的任务数 / 结果已知任务数。
- **完成耗时**：从接收请求到满足验收条件，包含路由与重试开销；用户等待时间单列。
- **用量**：按输入、缓存输入和输出等可用字段分别展示，遵循实际计数定义，避免重复相加。

试运行前固定任务分组和基线策略，在可控、可重复任务上进行对比。初始收益目标建议为：首次验收通过率下降不超过 5 个百分点，且完成耗时中位数或用量中位数至少改善 10%。这是待试运行校准的产品目标，不是已测结果；小样本只展示观察，不宣称因果收益。

## 10. 验收标准

| 编号 | 场景 | 预期结果 | 阶段 |
| --- | --- | --- | --- |
| A01 | 首次请求模型建议，未启用记录或执行 | 给出理由和生效范围；不启动执行、不写持久状态 | P0 |
| A02 | 用户明确指定有效模型和强度 | 保留明确选择，不被偏好或历史建议覆盖 | P0 |
| A03 | 指定模型不可用或强度不支持 | 显示不匹配原因与替代方案；不声称已采用 | P0 |
| A04 | 图片任务遇到纯文本候选 | 排除不满足要求的候选；无合格项时返回明确结果 | P0 |
| A05 | 可用列表缺失、过期或获取失败 | 标注不确定性；未经验证不能自动执行 | P0/P1 |
| A06 | 历史任务含模型切换、跨日活动、重复事件 | 按轮次和实际模型归属；未知保留，重复不累计 | P0 |
| A07 | 用户未反馈或只有模型自评 | 不直接计为已验收成功 | P0 |
| A08 | 自动策略已启用，请求进入支持入口 | 范围内执行一次并核对实际模型，无重复确认 | P1 |
| A09 | 自动策略已启用，但请求从不支持入口进入 | 明确覆盖限制，不显示自动切换成功 | P1 |
| A10 | 当前轮仍运行 | 保留本轮；选型仅供下一轮或下一次执行 | P1 |
| A11 | 单次覆盖作用于会持久化设置的接口 | 后续恢复策略预期值，或在执行前说明无法提供单次语义 | P1 |
| A12 | 超时但无法确认任务是否被接受 | 标为 unknown，核对状态前不重复提交有副作用的任务 | P1 |
| A13 | 依赖、认证或网络失败 | 正确归类，不据此自动升级能力 | P1 |
| A14 | 获准回退一次仍失败或预算耗尽 | 停止继续选型，报告已完成工作与剩余问题 | P1 |
| A15 | 用户暂停自动路由 | 后续不再自动启动；在途执行不被隐式取消 | P1 |
| A16 | 日志损坏或无法写入 | 报告失败并保留原数据；后续动作不伪装已记录成功 | P0/P1 |
| A17 | 项目 A 经验拟应用到项目 B | 保持项目边界，未经有效策略变更不全局推广 | P2 |
| A18 | 样本不足或请求恢复旧策略 | 展示证据缺口；恢复后仅改变后续选择，历史保留 | P2 |

以上为规划验收用例，不表示已经执行。后续实现需按仓库 [PR 审查手册](pr-review-playbook.md)建立覆盖台账，对持久化、启动执行、重试和恢复等入口检查直接调用及失败后状态。

## 11. 交付边界与实施顺序

推荐先在 `codex-usage-improvement` 产品范围内组织推荐和复盘，自动执行通过独立的 Codex 执行适配组件接入。是否拆出独立模型路由 Skill，在技术设计时根据触发和发布边界确定；不在 PRD 阶段新增空壳 Skill。

1. **数据契约与 P0**：确定每轮模型归属、结果来源、只读模式与记录模式，交付推荐和复盘。
2. **P1 可行性验证**：验证一个完整的“发现候选—提交—核对实际模型—接收结果”链路，以及上下文传递和重复执行控制。
3. **P1 产品化**：接入启停、项目策略、有限升级和失败处理。桌面入口验证与 CLI 入口分别报告，互不代替。
4. **P2 试运行**：建立可比较样本，接受一项策略调整并验证恢复行为，评价实际收益。

复用同一决策与结果契约是必要耦合；推荐、持久记录、CLI 执行和桌面接入可分别评审。通用工作流保留在 portable core，Codex 专用调用语法和能力适配遵循 [Agent Build 架构](agent-build-architecture.md)。

## 12. 风险与待决事项

| 事项 | 影响 | 草案默认或验证要求 |
| --- | --- | --- |
| 桌面当前任务的接口与 UI 同步 | 决定能否直接作用于用户正在使用的入口 | 必须实测版本、任务归属、轮次生效和显示一致性；未通过只推荐 |
| 初始模型池与预算 | 决定候选范围和升级边界 | 动态发现；用户启用自动模式时确定允许集合，不写死型号 |
| 质量评价 | 错误反馈可能让策略越调越差 | 验收证据和用户反馈优先；模型自评单列 |
| 路由额外开销 | 轻量任务可能比直接执行更慢、更耗量 | 首期规则优先，所有路由开销纳入指标 |
| 模型与运行时升级 | 同名策略在新环境下效果可能变化 | 记录版本，失效候选重新校验；新旧结果分组观察 |
| 记录保留期限 | 影响本机存储与隐私 | P0 实现前确定期限、清理入口和旧数据迁移策略 |
| 日志写入失败时自动执行是否继续 | 影响可追溯性与可用性 | P1 默认在提交前失败则不启动；提交后失败保留执行标识并报告，不重跑任务 |
