# Database Engineering

Produce database changes that preserve data semantics and can be assessed against the actual workload. Support PostgreSQL and MySQL/InnoDB; establish the engine before applying dialect-specific advice. Respect the user's existing hosting provider, ORM, migration tool, and authorization.

## Establish the Task

Inspect available project configuration, schema, migrations, and supplied plans first. Determine:

- Engine and server version, relevant extensions or storage engine, and deployment environment.
- Target database/schema and whether the request is an offline review, a file change, or live execution.
- Query and representative parameters, table sizes, indexes, read/write mix, and relevant latency or availability target.
- Existing migration runner, connection pool, tenancy model, and operational constraints when they affect the task.

Use existing evidence rather than requesting information already in the project. For an offline task, proceed with stated assumptions and identify what must be verified before execution. If the live target or required authorization is unclear, continue preparing a concrete plan and resolve that ambiguity before connecting or mutating. Never infer production access from a request to edit a migration file.

## Diagnose and Design

1. Establish a baseline proportional to the task. For a slow query, retain the SQL, representative parameter distribution, execution plan, latency, row estimates versus actuals if available, and relevant I/O or wait evidence. For a schema change, establish data invariants and application compatibility. A plan without measurements is a hypothesis, not proof of improvement.
2. Follow the evidence to a specific cause: access path, cardinality estimate, excess rows or columns, N+1 calls, lock waits, connection queueing, or resource pressure. An index scan is not inherently better than a sequential scan. Do not invent a performance percentage or change global configuration from one plan alone.
3. Preserve semantics when rewriting SQL: duplicates, NULL handling, outer joins, ordering, pagination ties, timezone boundaries, and transaction isolation. Use bound parameters for values and a validated identifier mechanism for dynamic identifiers.
4. Propose the smallest useful change with its write/storage cost and failure behavior. Select indexes from actual predicates, ordering, and workload, not a universal column-order rule. Read generated ORM SQL and migration output when the ORM is involved.
5. Validate changed behavior and performance separately. Compare representative workloads under comparable conditions; check result correctness, write latency, locks, and replication effects as applicable. If execution is unavailable, deliver the validation commands and mark the improvement unverified.

## Execution Boundaries

- Reuse authorization already given for the specific action and target. A request to diagnose or draft SQL does not authorize a drop, restore, global setting change, or production rollout. Prepare the exact SQL, target, impact, and recovery route before seeking any missing authorization; do not ask again when scope is already clear.
- Verify the connected server/database and effective role before any live change. Use available least-privilege access, bounded queries, timeouts, and filtered output. Do not print connection secrets, credentials, or unnecessary business rows into reports or logs.
- Plain `EXPLAIN` is the initial planning tool. `EXPLAIN ANALYZE` executes its statement: check statement effects and expected load first, including functions, triggers, and data-modifying CTEs. A read-only transaction does not prevent expensive reads or external effects; a rollback does not undo every possible side effect.
- Use [the change workflow](references/changes.md) before executing DDL, DML, restore, or maintenance. Confirm existing state after a timeout or disconnect before retrying; a lost response does not prove the command failed.

## Deliver the Result

Scale the output to the request. Identify the engine/version and scope, relevant findings and evidence, proposed or applied SQL/file changes, verification performed, and remaining assumptions. For live changes, also record the target, observed outcome, recovery route, and post-change health. Clearly distinguish prepared, executed, and verified work.
