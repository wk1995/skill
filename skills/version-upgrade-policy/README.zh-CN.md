# 版本升级约束

语言：**简体中文** | [English](README.md)

`version-upgrade-policy` 用于定义、选择、校验和应用项目自身的发布版本，涵盖初始值、升级级别、自定义格式、发布依据、版本 CI 检查，以及写入 AGENTS.md 的长期规则。项目指令要求评估版本影响时，普通代码变更也会触发；仅提及版本号或执行已选定版本的发布时不触发。

## 如何使用

提供当前版本、目标版本、变更内容以及项目已有的格式规则：

```text
使用 version-upgrade-policy 判断 2026.09.1 -> 2026.10.0 是否属于功能发布。
为 A.B.C 设计 CI 规则，其中 A 表示兼容性、B 表示能力、C 表示维护修复。
评审 1-rc-7 -> 1-rc-8 是否是合法的维护升级。
把版本升级约束补充到本项目的 AGENTS.md，让后续加功能、修 bug 时主动评估版本影响。
```

该 Skill 会记录版本语法、各部分含义、非数字后继规则、兼容性依据、changelog 要求和验证场景。具体操作见 [SKILL.md](SKILL.md)。

首次发布时，可以指定初始值，或采用项目已有规则要求的值；两者都没有时，默认使用数字版本 `0.0.1`。若明确选择的自定义格式无法表示 `0.0.1`，Skill 会询问符合该格式的初始值。已有发布不会重置为默认值，仅缺少版本文件也不代表组件是新建的。

写入长期规则时，指定目标项目或 AGENTS.md 的作用范围。Skill 会更新已有版本规则段落，或在缺少时创建，保留其他指令，重复执行不追加重复内容。规则采用项目实际格式和发布流程，让后续功能、修复任务无需额外提醒就评估版本影响；开发阶段写入 `[Unreleased]` 或已有 changeset，确定发布版本时统一升级一次。以后即使 Skill 不可用，已写入的规则也能提供核心指导。详见[集成指南与可复用规则](references/agents-integration.md)。

## 何时触发

当任务交付物或项目对当前任务的明确要求涉及**项目自身的发布版本**时触发：

| 请求 | 处理范围 |
| --- | --- |
| “把主动评估版本的规则加到 AGENTS.md。” | 在指定范围安装、更新或评审长期项目指令 |
| AGENTS.md 要求评估版本时，用户只说“加一个功能” | 即使未要求升级版本，也主动评估发布影响 |
| “给这个项目确定初始版本。” | 使用指定值或项目要求的初始值，否则默认数字 `0.0.1` |
| “修复后 1.2.3 应升到 1.2.4 还是 2.0.0？” | 判断是否需要升级及所需影响级别 |
| “把源码版本改成 1.2.4。” | 按已有规则校验并应用指定版本 |
| “定义四段版本或字母版本规则。” | 语法、各段含义、排序、后继及重置规则 |
| “把已有的单步升级规则接入 CI”或“修复会放过跳号的版本检查。” | 实现、评审或修复版本规则校验；不要求先制定新规则 |
| “这份 changelog 能否支持破坏兼容性的发布？” | 检查发布声明、兼容性和迁移依据 |

## 何时不触发

任务仅包含以下内容时不触发：

- 升级依赖、锁文件、运行时、SDK 或工具；按包管理器规则解析或比较第三方版本。
- 编译、测试、签名、打包、创建分支或标签、合并、发布、部署或回滚已选定的版本，例如“构建并发布 1.2.4”。
- 修 bug、加功能、优化代码或修改文档，且用户及项目规则均未要求版本策略工作或发布影响评估。
- 仅排版或翻译已有 release notes，不评估版本选择及其依据。
- 安装、同步、盘点或恢复 Skill 副本，不涉及发布版本策略。

排除规则优先于关键词匹配。“升级依赖，并确定应用的下个版本”只对应用版本判断部分使用本 Skill。
“升级一下版本”若未说明对象，先从上下文确认；仍不明确时，在修改前询问目标。
触发本 Skill 不额外授权发布、部署、创建标签或同步副本。
