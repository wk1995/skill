## 1. 建议结论

新增一个可扩展的 `email-management` Skill，统一处理“哪个账号、做什么、该账号能否执行”，按需调用现有 CLI、MCP 或平台原生 API。首期优先接入 **QQ 个人邮箱、网易 163/126、Gmail、飞书邮箱和允许 IMAP/SMTP 的工作邮箱**；第二阶段补充 Outlook/Microsoft 365、iCloud 和企业邮箱专用配置。

不为每个邮箱品牌复制一套 Skill，也不从零编写邮件客户端。供应商差异放在独立参考文档和能力表里。新增邮箱通常只增加一份接入说明、能力映射和验收记录；只有现有工具无法覆盖明确需求时才增加脚本。

这里的“首期接入”是实施目标。当前证据是官方文档、上游配置和部分源码核对，**尚无本仓库的真实账号联调结论**。每个后端必须通过第五节的能力核验和第九节的验收后，才能对外标为支持。

## 2. 邮箱支持范围

“工作邮箱”是账号用途，不是统一服务：虚构示例 `person@company.invalid` 可能由飞书、Google Workspace、Microsoft 365、腾讯、网易、阿里或自建服务器托管。接入时需确认实际服务商、服务器和组织权限，不能仅按域名猜后端。

| 邮箱或托管服务 | 拟用接入方式 | 接入条件与边界 | 阶段 |
| --- | --- | --- | --- |
| QQ 个人邮箱 | 优先评估用户提供的 `qq-email-mcp`；Himalaya IMAP/SMTP 为备选 | 开启 IMAP/SMTP，使用授权码；MCP 上游单账号，凭据保护存在平台差异，详见第三节 [S1–S3] | P1，满足凭据条件后启用 |
| 网易 163、126 | Himalaya CLI；需要 MCP 的环境再评估其 MCP 模式 | 开启客户端协议和授权码；服务地址使用对应产品官方说明；文件夹映射、中文检索和服务端客户端识别要求需实测 [S4、S10] | P1 |
| Gmail 个人邮箱、Google Workspace 邮箱 | `gws` CLI → Gmail API | OAuth、Google Cloud 项目和 Gmail API；个人 Gmail 与企业账号分别验收，企业管理员可限制授权；`gws` 项目明确不承诺 Google 官方产品支持 [S5–S6] | P1 |
| 飞书邮箱 | 官方 `lark-cli mail` | 已开通飞书邮箱、应用邮件权限及用户授权；普通飞书登录不等于开通邮箱。飞书与国际版 Lark 的环境分别确认 [S7] | P1 |
| 标准工作邮箱、自建域名邮箱 | Himalaya IMAP/SMTP | 管理员允许第三方客户端，提供经过确认的 TLS 服务器、端口、认证方式和凭据；只有 IMAP 时只能收信，只有 SMTP 时不能管理收件箱 [S4] | P1，条件支持 |
| Outlook.com、Hotmail、Microsoft 365 / Exchange Online | 优先评估 Microsoft Graph CLI（`mgc`）；Himalaya Graph 后端为备选 | OAuth 应用、账号类型、租户策略；分别核验个人账号和组织账号；不承诺任意本地 Exchange 或在线归档邮箱 [S8–S9] | P2 优先 |
| 腾讯企业邮箱 | 标准工作邮箱适配，补充供应商配置 | 与 QQ 个人邮箱分开配置；需补齐对应租户的官方服务说明和客户端权限证据，不能直接套用 `imap.qq.com` | P2，待供应商核验 |
| 网易企业邮箱 | 标准工作邮箱适配，补充供应商配置 | 与免费 163/126 分开配置；由管理员确认区域、服务器和认证方式 | P2，待租户核验 |
| 阿里企业邮箱 | Himalaya IMAP/SMTP | 管理员开启第三方客户端和协议权限；可使用第三方客户端安全密码；服务器使用官方当前配置 [S11] | P2 |
| iCloud Mail | Himalaya IMAP/SMTP | Apple 官方支持 IMAP/SMTP，使用 App 专用密码；需要先满足其双重认证条件 [S12] | P2 |
| 腾讯 Agently Mail | `agently-cli` | 官方提供 Agent 专用邮箱，与个人邮箱隔离；不代表获得现有 QQ 邮箱访问权 [S13] | P2，可选独立账号类型 |

## 3. 用户提供的 QQ MCP：调查结果

调查对象：[xieningqing/qq-email-mcp](https://github.com/xieningqing/qq-email-mcp)，源码快照 `e3b6015077ff3e1c4d69272e1fe67ff596fef613`。`package.json` 声明版本 `0.1.1`、MIT 许可、Node.js `>=20.19`；这些是源码元数据，不代表已核验 npm 分发包与该提交一致 [S1–S2]。

### 3.1 已声明的能力

项目通过本地 stdio MCP 连接 QQ 官方 IMAP/SMTP，提供 10 个工具 [S1]：

| 工具 | 用途 |
| --- | --- |
| `mail_status`、`mail_folders` | 账号、连接状态、权限、服务端能力和文件夹映射 |
| `mail_list`、`mail_search`、`mail_digest` | 列表、搜索、分页、近期邮件概览 |
| `mail_get` | 元数据、分段正文、线程或模型上下文 |
| `mail_attachment` | 附件读取、下载和部分文档文本提取 |
| `mail_draft` | 在 Drafts 中创建或替换草稿，不发送 |
| `mail_send` | 新邮件、回复、全部回复、转发 |
| `mail_update` | 已读/未读、星标、移动、归档、移入垃圾箱 |

上游说明还包括引用历史整理、原附件转发和 PDF/DOCX/XLSX/PPTX 文本提取。上述是上游能力说明；本次没有执行附件解析或真实邮件操作，不能声称效果已经验证。

### 3.2 对接时必须处理的限制

1. **单账号与隔离。** 一个服务实例对应一个账号，默认凭据文件也只存一份账号。多账号需分别隔离实例、配置、凭据、附件目录和日志，并校验实例返回的真实账号。不得重复初始化同一个默认文件来“切换账号”。
2. **默认权限。** 配置默认只读；草稿、更新和发送需要开启对应权限。读连通与完整就绪分开判断：IMAP 可读不代表 SMTP 可发，不能为了查询收件箱强制用户开放发信。
3. **确认机制。** 发信预览产生一次性令牌；确认存储默认有效期 10 分钟。源码存在 MCP 客户端 elicitation 分支。拿到令牌本身不证明用户已经同意，Skill 不能自动回传令牌当作用户确认 [S3]。
4. **凭据差异。** Windows 可使用 DPAPI；非 Windows 使用主机名和用户名派生的 AES 密钥，上游明确称其为混淆。当前设备为 macOS，后续若采用此后端，应优先评估系统钥匙串注入子进程凭据的方式，或选择具备合适凭据来源的替代后端；不直接把默认文件称作强加密保险箱 [S2]。
5. **发信状态。** SMTP 接受与送达分开报告；部分收件人被拒绝、发出后保存已发送副本失败，应分别返回，不能为补存副本自动再发邮件。
6. **删除和重试。** 上游不提供永久删除；只读断线重试与写操作区分，发信结果不明时禁止自动重发。

建议将它作为 QQ 专用候选后端保留，并优先做 macOS 凭据、多账号隔离和分发包核验。它不是腾讯官方 MCP，也不是所有邮箱通用的后端，不能仅修改 SMTP 地址就承诺支持其他品牌。

## 4. 其他工具选型与依据

### 4.1 通用后端：Himalaya

[Himalaya](https://github.com/pimalaya/himalaya) 源码快照 `42134fd20ca6d37aa86e02d6777487231cfe7032` 的包版本为 `2.2.1`。当前源码文档包含多账号配置、结构化 JSON 输出、IMAP/SMTP 和多个 API 后端，也提供 stdio MCP [S4]。

建议先用 CLI 接通网易和标准工作邮箱，利用现有工具处理协议、MIME 和邮件操作。需 MCP 时，一个 MCP 进程绑定一个账号，不能把 CLI 的多账号配置误写成单实例 MCP 任意切换账号。

MCP 默认仅公开读工具，写入和发送分别由启动选项控制；CLI 则不天然具有相同工具隔离。实施时分别核验两个入口的权限边界。源码新能力不能推定已包含在任意 Homebrew 或历史发布包中，必须固定实际安装版本，检查帮助、工具清单和构建特性。

### 4.2 Gmail：优先 `gws`，官方 MCP 作为可选预览

[`googleworkspace/cli`](https://github.com/googleworkspace/cli) 提供结构化输出和 Gmail 操作，通过 Google Discovery 构建命令。它位于 Google Workspace 组织下，但 README 明确说明不是 Google 官方支持的产品，不能将其维护主体与服务承诺混为一谈 [S5]。

Gmail API 可覆盖消息、会话、草稿、标签和附件，适合 Gmail 语义。OAuth scopes 要按读、草稿、发信和管理需求选择；部分 scopes 属于敏感或受限范围，不能承诺所有个人账号都能无额外配置登录 [S6]。

Google 已发布 [Gmail 官方远程 MCP 配置文档](https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server)，但处于 Developer Preview，要求预览计划成员资格和相应 Cloud/OAuth 配置。文档列明读取、创建草稿和标签操作；未经过工具清单核验的发送等能力不能从 REST API 自动推定到 MCP。首期默认走 CLI，已有资格且明确选择该路线的用户可单独评估官方 MCP。

### 4.3 飞书：复用官方邮件 CLI

[`larksuite/cli`](https://github.com/larksuite/cli) 已有邮件操作及官方 `lark-mail` 指引，支持查询、正文、线程、草稿和发送流程。发送快捷方式默认保存草稿，实际发送需显式标志；发信路径使用用户身份 [S7]。

基础邮件操作纳入首期；规则、模板、公共邮箱、别名、定时发送和监听作为可选增强，分别核验 scopes、账号资格及命令版本。飞书邮箱与“在飞书客户端绑定了某个第三方邮箱”不是相同的开放能力，后者不能自动视作已接通。

### 4.4 Microsoft：Graph CLI 优先评估

[`microsoftgraph/msgraph-cli`](https://github.com/microsoftgraph/msgraph-cli) 提供跨平台 Graph 命令及交互式/设备码等认证策略。邮件支持范围以 Graph v1.0、实际 CLI schema 和账号授权交集为准；Himalaya 的 Graph 后端保留为替代选项 [S8]。

权限上，`Mail.ReadWrite` 不包含发信，`Mail.Send` 需独立考虑。首选用户委托权限，不默认申请租户全部邮箱的应用权限。传统本地 Exchange、共享邮箱与归档邮箱另设边界，不作普遍支持承诺 [S9]。

Microsoft 官方旧版 Mail MCP 文档已注明仅为兼容保留，不建议用于新项目，并指向 Work IQ MCP。因此不将网上旧的 `mcp_MailTools` 配置作为通用默认方案；Work IQ 的产品资格、客户端范围和部署条件需另行评估 [S14]。

### 4.5 Agently Mail：可选新增邮箱，不替代原邮箱

腾讯官方仓库明确其服务与个人邮箱隔离。适合用户想给 Agent 一个专用邮箱的场景，可复用官方 CLI 的授权、收发、附件和确认流程。它不能证明普通 `@qq.com` 个人邮箱可通过该 CLI 接入，故独立列为账号类型 [S13]。

## 5. 功能设计与差异

“支持某邮箱”不是无条件拥有所有功能。能力来自四项交集：**后端实际版本 × 服务端能力 × 账号权限 × 本次用户授权**。

### 5.1 首期功能和后端映射

以下为拟实现映射，均待真实账号验收。“条件”表示不能建立统一保证。

| 功能 | QQ MCP | 网易/标准 IMAP/SMTP（Himalaya） | Gmail（gws/API） | 飞书（lark-cli） |
| --- | --- | --- | --- | --- |
| 账号识别、连接和权限诊断 | 状态工具 | 配置与连接检查 | OAuth/API 检查 | 用户身份与邮箱授权检查 |
| 收件箱、未读、分页、时间筛选 | 有对应工具 | 列表与查询，语法适配 | 消息查询 | 邮件查询 |
| 发件人/主题/关键词搜索 | 有对应工具 | 服务端查询能力有差异 | Gmail 查询语法 | 飞书查询/过滤 |
| 正文、附件元数据、普通附件下载 | 有对应工具 | 有对应命令 | 消息和附件 API | 邮件和附件接口 |
| AI 摘要、翻译、提取待办、撰写 | Skill 对读取结果处理 | 同左 | 同左 | 同左 |
| 云端草稿 | 创建/替换 | 条件：Drafts 映射和追加能力 | drafts API | 草稿流程 |
| 新邮件、回复、全部回复、转发 | send 模式映射 | 组合 MIME/线程头和 SMTP，需验证 | API/快捷方式 | 默认草稿，显式发送 |
| CC/BCC、普通发送附件 | 有，按限额 | 条件：命令/MIME 与服务端限额 | 条件：API/CLI 路径 | 条件：上传与发信权限 |
| 已读/未读、星标 | 更新工具 | flags，服务端支持有差异 | labels/消息修改 | 标记/标签接口核验 |
| 移动、归档、移入垃圾箱 | 更新工具 | 条件：文件夹角色与安全移动能力 | 标签及 trash 语义 | 文件夹/标签语义 |
| 原生线程 | 上游聚合 | 条件：邮件头聚合，不保证等同网页线程 | 原生 thread | 原生 thread |
| 全局标签、规则、实时监听 | 不作首期承诺 | 不作统一承诺 | 后续增强 | 后续增强 |

摘要、翻译和分类由当前 Agent 在用户选定范围内完成，不意味着每个后端内置 AI。默认不会把整个邮箱同步到新数据库或第三方模型服务。提取待办先展示文本，不自动向任务、日历或 IM 服务写入。

跨账号查询必须显式选择账号集合，逐账号返回来源、查询范围、分页状态和失败信息。单个账号失败时结果标为不完整，不能把它当作“无邮件”。不自动遍历用户所有账号，也不默认复制邮件到另一个邮箱。

### 5.2 语义和限制

- Gmail 标签与 IMAP 文件夹不同。“归档”需映射为对应服务语义；没有可靠映射时返回不支持，不能用删除代替。
- 初次读邮件应尽量保持未读，明确检查是否会标为已读。正文被截断、只搜索了部分文件夹或只取到部分分页时必须说明。
- 回复须保留对应后端的线程标识或 `In-Reply-To` / `References`；全部回复应展示最终 To/CC 并避免重复自身地址。
- 附件上限取后端、服务端与本地配置的最小值；普通附件、网盘链接和超大附件区分处理，不将链接文件宣称为已下载。
- 首期只保证经过验收的普通附件处理。文档文本提取按可用解析器启用；扫描件 OCR、加密附件、数字签名和复杂版式不作统一保证。
- “已发送”仅在后端确认提交后报告；不等同于对方已送达或已读。结果不明、部分失败和副本保存失败须保留原始状态。

初版完整 Skill 已建立，四份设计文件和本轮实施记录已迁入所属 Skill 的 `doc/`。原仓库级目录不再保留副本；当前相对链接随文档归属使用，指向历史提交的来源证据保持原样。真实账号及邮箱执行证据不随迁移入仓库。

初版不开发统一邮件 CLI/MCP 服务，也不新增常驻进程或中心账号数据库。新增本机账号引用工具负责非秘密 JSON 索引的校验、私有保存和原子替换；不存凭据、不启动邮件后端、不替代原生身份检查。其他邮件操作通过 Skill 编排已有工具，具体实现边界见[本地存储](../references/local-storage.md)。

### 6.2 路由与能力记录

每次任务按以下顺序处理：

1. 从仓库外的本机账号配置和可见连接确定候选账号，结合用户请求选择；多个候选且无法确定时，先明确使用哪个账号。不得从仓库内配置读取或保存真实账号。
2. 尊重用户已指定的工具；否则优先使用已连接、身份正确且能力足够的后端，再考虑表中的默认后端。
3. 只加载对应供应商说明，确认实际工具版本、账号身份、授权和本次操作能力。
4. 将任务映射到原生命令；同一事务内固定后端，错误不触发静默切换账号或重做发送。
5. 按查询、草稿、管理或发送类别执行，保留原生引用和实际结果。

能力记录至少覆盖以下概念；这些是设计字段，不代表当前存在对应 CLI 或配置文件：

| 字段 | 作用 |
| --- | --- |
| `account_id`、`address`、`provider` | 逻辑账号、经连接校验的真实地址和实际托管类型 |
| `backend`、`backend_version`、`instance` | 后端种类、版本及实例标识；多个实例不能共用默认凭据文件 |
| `capabilities` | read/search/attachments/draft/send/flags/move/trash/thread/watch 等独立能力 |
| `auth_state`、`limits` | 授权有效性、附件限额和查询范围 |
| `native_ref` | 后端不透明引用；始终与账号、后端实例绑定 |
| `observed_at`、`evidence` | 验证时间和对应命令/工具结果，不记录令牌或正文 |

查询结果中的引用绑定账号与实例。IMAP 引用还需包含文件夹、UIDVALIDITY 和 UID；失效时重新查询。Graph 等移动后可能变化的 ID 按原生约束重新解析。不能把两个账号恰好相同的 message ID 当作同一封邮件。

### 6.3 新增邮箱流程

确认真实服务和授权方式 → 评估能否复用现有后端 → 补充供应商参考文档与能力差异 → 用测试账号核验 → 更新双语用户文档和根目录生成目录 → 在 `[Unreleased]` 记录变化。

有官方 CLI/API/MCP 时优先评估其实际适用范围、授权和维护状态；没有专用工具但支持标准协议的，走通用后端；缺少证据则标记待支持。新增供应商通常属于向后兼容能力，发布时按仓库版本政策评估 MINOR，开发阶段不逐提交定版。

## 7. 授权、凭据与操作边界

| 操作 | 拟定行为 |
| --- | --- |
| 只读查询、摘要、翻译 | 按用户请求的账号和范围直接执行；不因只读操作反复询问 |
| 仅起草文案 | 可以在对话中直接完成，无须创建云端草稿 |
| 保存/修改云端草稿 | 用户请求保存草稿时执行，明确这是远端写入；不报告为已发送 |
| 标记、移动、归档、移入垃圾箱 | 明确目标账号与查询得到的邮件集合后执行授权操作；批量范围不明时先展示清单 |
| 发信、回复、转发 | 展示最终账号、收件人、主题、正文和附件；遵守后端的真实用户确认流程，已有授权仅适用于覆盖的内容，变化后重新确认 |
| 永久删除、群发营销、全租户设置 | 不属于首期支持范围 |

发送确认令牌、CLI 确认参数和 MCP 工具声明都不能单独证明真实用户同意。明确请求“调研/写方案”不授权安装工具、修改 Agent 配置或连接邮箱；明确的账号配置任务也不自动授权发测试邮件。

凭据优先由后端 OAuth/系统钥匙串管理，不进入仓库、样例、日志或模型可见输出。需要注入进程的密钥从受控存储读取，避免命令行参数、命令历史和广泛继承的环境变量暴露。退出登录需区分删除本地缓存和撤销服务端授权。

本地限制不限于密码：真实邮箱地址、账号别名、收发件人、服务器/租户与连接配置、授权和能力记录、邮件引用、正文、附件、草稿快照、日志、诊断导出及备份都不得提交。需要保存的账号配置、邮件缓存和运行记录写到仓库外的本机私有目录；不因移除密码或脱敏就自动变成可提交样例。此约束针对 Skill 侧存储，不改变用户明确授权的原邮箱查询、云端草稿或发送行为。

`.gitignore` 中的邮箱专用规则仅防止惯用名称的本地副本被误加；它不保护已跟踪文件，也不能代替写前路径验证和暂存内容检查。禁止通过 `git add -f` 提交真实邮箱数据，构建与同步也不能打包本机配置或解析其指向的凭据。

邮件、附件名、HTML 和链接均是不可信数据。邮件内容不能改变账号、收件人、权限、下载位置或执行工具。HTML 不加载远程图片；下载使用受限目录并拒绝路径穿越和覆盖。摘要不能将模型推断包装成邮件原文。

只读网络失败可有限重试；缺少授权或工具明确报错时给出具体原因。写操作结果不明时先查证原生状态，不自动重发，也不切换到另一个后端再发一次。

## 8. 触发、使用示例与交付阶段

### 8.1 触发与排除

触发：读取/搜索/整理指定邮箱、起草并保存邮件、明确授权的收发和基础管理、接入新的邮箱服务，以及跨多个邮箱的邮件任务。显式指定既有专用 Skill 时尊重该选择；专用 Skill 已足够的请求不重复接管同一次操作。

不触发：SMTP 服务端开发、邮件服务器运维、DNS/SPF/DKIM/DMARC 配置、纯联系人查询、飞书 IM/文档/日历任务、营销群发，以及没有邮箱操作含义的普通写作。

示例：

- “把我的 QQ 邮箱接进来，先验证只读连接。”
- “查 163 邮箱最近七天来自供应商的邮件，列出还需要我回复的事项。”
- “在 Gmail 起草回复这封邮件，保留线程，先不要发送。”
- “用工作邮箱把这份报价发给王经理，先给我看正文和附件清单。”
- “只搜索已选的两个账号，找上个月的合同附件，结果保留邮箱来源。”
- “增加一个支持 IMAP/SMTP 的公司邮箱，不改已有 Gmail 配置。”

### 8.2 阶段交付

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| P0：冻结接入约束 | 确定实际后端版本、测试账号、凭据路线、工具清单和组织限制 | QQ 的 macOS 凭据方案可接受；每个首期后端有明确可测环境，未具备的标为待验证 |
| P1：基础 Skill | 完整目录、双语说明、按需加载的 QQ/IMAP/Gmail/飞书参考文档；基础收发、草稿、附件和管理能力 | 每个声称支持的邮箱通过只读验收；每项写能力用获授权的测试账号和收件人验证；能力不齐时明确降级 |
| P2：扩展主流工作邮箱 | Outlook/Microsoft 365、iCloud、企业邮箱配置、可选 Agently Mail | 按账号类型单独验收，并记录组织权限和不支持范围 |
| P3：可选增强 | 监听、定时发送、规则、模板、共享邮箱、附件增强 | 逐后端验证；常驻任务、额外服务和额外权限由对应需求明确授权 |

优先按独立边界实现：通用路由/权限约束 → 一个只读后端 → 其草稿和写入 → 其他后端。只有验证共享约束确实一致后才提取公共脚本。新邮箱不会阻塞既有后端继续使用。

发布前固定并核验实际分发包及许可；不能用浮动 `latest` 作为可复现依据。按仓库规则最终确定 Skill 版本与 changelog，不在本方案阶段创建版本或发布声明。

## 9. 验收计划与本次覆盖记录

### 9.1 实施验收矩阵

每条用例按“后端 × 实际版本 × 账号类型 × 入口（CLI/MCP）”记录，不能用一个账号或单一入口的成功代表全部支持。

| 不变量 | 入口与场景 | 应验证的结果 |
| --- | --- | --- |
| 不跨账号操作 | 两账号查询到相同原生 ID；单账号 MCP 误接配置；错误实例或别名 | 在首次远端写入前拒绝身份错配，未选账号不变 |
| 读取不会暗中写入 | 未读邮件正文、附件、分页读取，读权限缺失 | 尽量保持未读；无法保证时先披露；无权访问明确失败 |
| 查询范围真实 | 多页、时区边界、中文、空结果、某账号离线 | 分页和筛选不丢失；部分失败不能表现为完整空结果 |
| 草稿与发送区分 | 起草、云端保存、更新带附件草稿、发送已保存草稿 | 草稿不发出，线程和附件保持正确，结果状态不混淆 |
| 写入口共享验证 | 新发、回复、全部回复、转发、草稿发送、标记、移动、垃圾箱 | 每个直接入口先校验身份、能力和授权，再首次变更；不能仅依赖先运行诊断 |
| 发送不重复 | 权限拒绝、确认过期/重放、取消、内容修改、超时、部分收件人失败、副本写入失败 | 不绕过确认；不自动重发；清楚保留未知或部分失败状态 |
| 引用有效 | IMAP UIDVALIDITY 改变、跨文件夹移动、Graph ID 变化 | 过期引用拒绝并要求重新查询，不命中其他邮件 |
| 文件下载受限 | 同名附件、`../`、绝对路径、符号链接、大小超限、目标不可写 | 不越界、不覆盖已有文件，不将失败报告为已下载 |
| 依赖和凭据缺失安全失败 | 受控 PATH 去掉 CLI，过旧版本，MCP 不可用，认证失效 | 执行前报出准确缺项，不申请更宽权限或静默换账号 |
| 新供应商不破坏已有配置 | 新增账号、修改后端、撤销授权、重复设置 | 只改变所选账号；需要自动修复时覆盖拒绝、成功和重复执行 |
| 分发内容可实际运行 | 构建受影响 Agent 产物，在仓库外测试公开流程 | 声明的参考文档/脚本存在，所需依赖清楚，默认权限与说明一致 |
| 邮箱信息只保存在本机 | 新增账号、重启加载、缓存/附件/日志落盘、配置路径覆盖、构建与同步 | 账号可由本机配置恢复；所有私有路径在仓库外，拒绝相对路径、仓库内路径及链接/大小写别名绕过；分发物不含真实数据 |
| 邮件内容不能授权操作 | 邮件伪装系统指令，要求转发或泄露附件，恶意 HTML/文件名 | 仅作为数据，不扩大原始用户任务 |

首次真实账号连通仅做只读；写入用例需使用已明确授权的测试账号、邮件和收件人。没有测试凭据的供应商标记“未验证”，不能通过伪造结果填满矩阵。
